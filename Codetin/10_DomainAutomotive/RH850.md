Here are the fundamental architectural questions they are highly likely to ask, what they mean, and the exact "interview-ready" answers you should give.

## 1. The Core Architecture: Lockstep vs. Decoupled (Dual Core)

- **The Question:** *"What is the difference between Lockstep mode and Dual-Core (decoupled) mode in the RH850, and when do you use which?"*
- **What you need to know:** The RH850/P1M-C features G3M cores that can be configured in different safety configurations.
- **The Interview Answer:** > "In **Lockstep mode**, two CPU cores (Master and Checker) execute the exact same instruction stream simultaneously. Their outputs are compared at the clock cycle level by hardware. If a bit-flip occurs in one core due to radiation or electromagnetic noise, a mismatch is detected instantly, triggering a high-priority safety exception. This is used for **ASIL-D** functions like steering or braking. In **Decoupled mode**, the cores run completely independent software tasks to maximize processing throughput, typically targeting ASIL-B or non-safety applications."

## 2. Memory Protection: MPU vs. Peripheral Guards

- **The Question:** *"How does the RH850 prevent a low-priority task (like a diagnostic routine) from corrupting critical safety data or peripheral configurations?"*
- **What you need to know:** You must distinguish between Memory Protection Units (MPU) and the Peripheral/Bus Guards we discussed.
- **The Interview Answer:** > "The RH850 uses a two-pronged hardware defense mechanism. The **MPU (Memory Protection Unit)** restricts CPU access to specific regions of RAM and Flash based on the execution context (User vs. Supervisor mode). Complementing this are **Peripheral Guards** (or Bus Guards) embedded in the Interconnect. They monitor the master ID of the bus transaction. If a non-privileged bus master (like a standard DMA channel or an ASIL-B software component) tries to write to an ASIL-D peripheral register, the Interconnect blocks the write and generates a bus error."

## 3. Flash Memory Structure: Code Flash vs. Data Flash

- **The Question:** *"Why does the RH850 separate Code Flash from Data Flash, and what are their hardware differences?"*
- **What you need to know:** It's about read-while-write capability and endurance.
- **The Interview Answer:** > "**Code Flash** is optimized for high-speed, wide-bus instruction fetching (often with caching) and has lower write-cycle endurance (typically 1,000 to 10,000 cycles). **Data Flash** is designed to mimic EEPROM for storing non-volatile calibration data, DTCs, and security keys. It supports **Read-While-Write (RWW)**, meaning the CPU can execute application code from Code Flash while simultaneously erasing or writing a block in Data Flash without stalling. It also has a much higher endurance (typically 100,000+ cycles)."

## 4. Hardware Security: The ICU (Intelligent Cryptographic Unit)

- **The Question:** *"What is the purpose of the ICU (e.g., ICU-M) in the RH850, and why can't we just do crypto in software?"*
- **What you need to know:** This ties directly to your work with **SecOC** and Secure Boot.
- **The Interview Answer:** > "The **ICU** is a dedicated, isolated hardware security subsystem with its own secure processor, cryptographic accelerators (like AES-128/256), and isolated secure RAM/Flash for key storage. We use it because doing cryptographic operations (like verifying a SecOC MAC) in software heavily taxes the main CPU and introduces timing jitter. More importantly, the ICU provides physical isolation; the main CPU core cannot access the private keys directly, protecting the cryptographic assets even if the main application software is compromised by an exploit."

## 5. Clock Domains & Low Power (Option Bytes)

- **The Question:** *"How are clock domains isolated in the RH850, and how does the chip boot up securely?"*
- **What you need to know:** Mentioning "Option Bytes" shows you've actually worked with the hardware flash tools.
- **The Interview Answer:** > "The RH850 separates the clock tree into distinct domains: high-speed clocks for the CPU and H-Bus, and decoupled, divided clocks for the P-Bus peripherals to reduce power consumption and EMI. For boot configuration, the RH850 uses **Option Bytes**—special flash registers read by the hardware resets before the CPU executes its first instruction. Option Bytes dictate the initial clock settings, watchdog configurations, and whether the ICU-M should enforce a Secure Boot sequence before releasing the main G3M core from reset."

### Pro-Tip for the Interview

When they ask you a fundamental question about the buses (like H-Bus vs. P-Bus), don't just say, *"One is fast and one is slow."* Frame it like an automotive engineer: **"The H-Bus ensures memory access latency doesn't bottleneck control loops, while the P-Bus isolates peripheral register modifications behind hardware safety guards to maintain ASIL-D integrity."** This immediately shows them you understand systemic architecture, not just code compilation.
